# Design — 设计与契约

让"怎么做"先于"写代码"确定，并让**跨端以契约为边界**，而不是互相猜。

## 何时使用

- 新功能涉及接口、数据模型、模块边界变更时
- 多端并行开发（Web / 移动端 / 后端）需要定接口时
- 出现需要记录取舍的架构决策时（不记录＝下次还要再吵一遍）

## 一、架构决策记录（ADR）

- 位置：`docs/design/ADR.md`（模板见 `templates/ADR.md`），一条决策一节，**只追加、不改写历史**；被推翻时新增 ADR 并在旧条目注明"被 ADR-XXX 取代"。
- 每条必须含：背景/问题、决策、理由、**后果（含代价）**、替代方案、影响面。
- 涉及架构/接口/数据模型变更 → 触发**人工确认闸门 ②（架构闸门）**。

## 二、接口契约先行

- **单一来源**：契约文件放在 `docs/api/`（如 `openapi.json`），是前后端与移动端的唯一接口真相。
- **先定契约，再写实现**：契约评审通过后才允许并行开发；实现与契约不符即为缺陷。
- **可机器校验**：契约必须是合法且结构完整的文档 → 用 `scripts/check-contract.mjs` 校验（纳入门禁）。
- **变更管理**：破坏性变更必须升版本 + 给出兼容期；同一路径/字段不得在多处硬编码。
- 契约类型按栈选择：HTTP API → OpenAPI；事件/消息 → JSON Schema 或 Proto；内部模块边界 → 类型定义 + 校验。

## 三、数据模型与迁移

- 实体/关系先落文档（`docs/design/`），再建表；避免"边写边改表"。
- 迁移脚本**可重入、可回滚**（含 down 或补偿方案）；迁移审查走发布预检清单。
- 破坏性 schema 变更（删列/改类型）必须有数据回退方案。

## 输出物

| 文件 | 内容 |
| :-- | :-- |
| `docs/design/ADR.md` | 架构决策记录（追加式） |
| `docs/api/openapi.json` | 接口契约（机器可校验，`check-contract.mjs`） |
| `docs/release/RELEASE_CHECKLIST.md` | 迁移与回滚方案（与 release 技能联动） |

## 禁止

- ❌ 无 ADR 的重大架构/接口/数据模型变更
- ❌ 契约未定就并行开发，或改契约不通知调用方与移动端
- ❌ 迁移不可重入或不可回滚
- ❌ 把接口字段直接透传、不做显式转换（见编码规范各栈分层要求）
