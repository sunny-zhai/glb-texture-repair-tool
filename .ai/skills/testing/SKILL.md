# Testing — 测试策略与门禁

把"写完了"变成"**有证据地证明它对**"。大模型最容易跳过这一步，本技能把它固化为流程环节。

## 测试分层（按投入优先级）

| 层 | 范围 | 工具（示例） | 何时必做 |
| :-- | :-- | :-- | :-- |
| 单元 | 纯函数、核心分支、边界 | pytest / Vitest / Jest / JUnit | 所有新增逻辑 |
| 集成 | 模块间、DB/SQL、API 契约 | pytest + Testcontainers / @MybatisTest | 涉及数据/外部边界 |
| 契约 | 前后端接口一致性 | OpenAPI/Schema 校验 | 多端并行开发时 |
| 组件/UI | 空/加载/异常态、交互 | Testing Library | 页面/组件改动 |
| E2E | 关键用户路径 | Playwright / Detox | 核心流程（登录/支付） |
| 快照/视觉 | 结构或视觉回归 | 快照测试 / 截图比对 | UI 重构、设计契约变更 |

## 执行节奏（TDD 红绿）

1. **红**：先写失败的用例（对应 REQ 的验收标准），确认它**确实失败**。
2. **绿**：以最小实现让其通过。
3. **重构**：在用例保护下清理。
4. **回归**：跑相关子集 → 再跑全量，确认无破坏。
5. **证据**：把命令与结果写入项目任务（`docs/requirements/TASKS.md` 的"验证结果"）。

## 覆盖率门槛（按场景）

| 场景 | 门槛 | 说明 |
| :-- | :-- | :-- |
| 核心逻辑 | ≥95% | 计费、权限、状态机、数据一致性 |
| 测试代码 | ≥90% | 关键断言路径 |
| 文档 | ≥90% | 有对应产物与命令 |
| UI 组件 | ≥85% | 主要状态与交互 |
| 探索性原型 | ≥70% | 允许低覆盖，但必须显式标注 |

- 门槛**由用户按场景确认**，不自动放宽；放宽需在需求或 ADR 中记录原因。
- 覆盖率**不是目标**：禁止为凑数字写空断言；优先覆盖**分支与边界**（空集合、超大值、并发、权限不足、异常路径）。

## 必测清单（每个功能点）

- 成功路径 · 非法参数 · 无数据/空集合 · 权限不足 · 外部失败（超时/网络） · 重复操作/幂等 · 数据边界（0/最大/超长）

## 禁止

- ❌ 无验证结果就声称完成（"看起来没问题"式放行）
- ❌ 只覆盖成功路径
- ❌ 为覆盖率写无意义断言或 sleep 式等待
