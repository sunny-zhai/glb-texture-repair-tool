# Requirements — 需求工程与追溯

把一个"想做什么"变成**可验收、可拆解、可追溯**的需求，避免大模型在缺约束时做偏。

## 何时使用

- 新项目立项、新功能、需求变更、缺陷需要明确验收标准时
- 任何"开始写代码之前"的时刻（平台规则：**文档先行**，无规格就写代码属流程违规）

## 输出（写入项目）

| 文件 | 内容 |
| :-- | :-- |
| `docs/requirements/REQUIREMENTS.md` | 需求清单：`REQ-XXX` + 验收标准 + 追溯 |
| `docs/requirements/TASKS.md` | 任务拆解：`TASK-XXX` + 依赖 + 验证方式 |

模板见 `templates/REQUIREMENTS.md` 与 `templates/TASKS.md`（复制后填写）。

## 步骤

1. **澄清**：向用户确认目标、边界、不做项、约束；歧义必须问，不要猜。
2. **立需求**：为每条需求分配 `REQ-XXX`，写**验收标准**（Given/When/Then），每个功能点 **≥5 个验收场景**（平台文档质量标准）。
3. **拆任务**：把需求拆成**可独立验证**的任务 `TASK-XXX`；标注依赖，形成 DAG；每个任务必须写明"如何验证"。
   同时标注**文件范围**（预计改动的路径），并据此排出**并行批次**：
   - 文件范围**不重叠**且依赖已满足 → 同一批次可并行
   - 文件范围**重叠** → 必须排入不同批次（并行会冲突）
   - 合并与批次无关：**合并严格一次一个**，不做并发合并（见 `.ai/workflows/req-parallel.js`）
4. **建追溯**：`REQ ↔ TASK ↔ 代码/测试` 双向可查：
   - 任务的"关联需求"填 REQ ID
   - 代码/测试中标注所属 REQ（注释或测试名，如 `test_req_003_login_rejects_bad_password`）
5. **闸门**：需求与验收标准**由用户确认后**才进入实现（人工确认闸门 ①）。

## 硬性要求

- **无 REQ ID 不得进入实现**；找不到 ID 必须暂停并询问。
- 每个 REQ 至少一条**可自动或可手工判定的验收标准**（避免"看起来没问题"）。
- 任务粒度：**单个任务应能在一次会话内完成并独立验证**（否则继续拆）。
- 需求变更：更新 REQUIREMENTS.md 并记录变更原因；不要静默改行为。

## 禁止

- ❌ 需求未确认就开写代码
- ❌ 验收标准写成"功能正常""性能良好"这类不可判定表述
- ❌ 任务无验证方式、或无依赖关系地一把梭
