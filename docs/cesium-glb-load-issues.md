# Cesium GLB 加载问题：排查与修复备忘（团队分享）

> **给谁看**：遇到「这个 GLB 在 Cesium 里加载成功、但画面黑屏/空白/看不到模型/姿态不对」的同事；以及使用“GLB 贴图修复工具”的同事。
> **什么时候看**：模型在 3D 查看器/游戏里正常，换到 Cesium 就不对的时候，先翻这份文档。
> **基于**：2026-09 实测的三组伤情人物模型（蹲姿 / person-move / person-stand）与修复工具的实际行为整理。

---

## 0. 一句话结论（TL;DR）

大多数“Cesium 看不到/不对”的问题，**不是 Cesium 坏了**，而是 GLB 里有四类东西和 Cesium 的运行方式不兼容：

| 问题 | 一句话根因 | 处置 |
|---|---|---|
| 贴图黑/丢失、`Failed to load texture` | 贴图是**外部路径**，Cesium 拿不到本机文件 | 把贴图**内嵌**进 GLB |
| 带 JPG 贴图的模型材质加载失败 | JPG/异常格式在 Cesium 侧不稳 | **统一转 PNG**（进程内 `jpeg-js`+`pngjs`）；代价是照片类贴图约膨胀 5 倍，靠降采样而非保留 JPEG 解决 |
| 有 `KHR_materials_specular` 等扩展 | 扩展兼容性风险 | 移除相关扩展声明 |
| 蒙皮角色“加载成功但不显示” | `skins`+`JOINTS_0/WEIGHTS_0` 网格 Cesium 不一定画得出 | **烘焙成静态网格** |
| 蒙皮角色修完“全变成站姿/都一样” | 动作在**动画剪辑**里，烘焙用了绑定站姿 | **先冻结动画里的目标姿势**再烘焙 |
| 明明有模型却看不到/被裁切 | 相机取景/包围球不对 | 按包围球取景、更保守的近裁剪面 |

下面把每一条的原理、判断方法和正确姿势讲清楚。

---

## 1. 背景：我们的模型是什么

伤情人物模型通常是 **3ds Max / FBX → GLB** 转出来的，普遍带这几样特征：

- 一个 **Mixamo 骨骼**（`mixamorig:Hips` 这类命名），52 个关节左右；
- 皮肤网格：每个顶点带 `JOINTS_0`（4 个关节索引）+ `WEIGHTS_0`（4 个权重）；
- 一到多段 **动画剪辑**（动作是“演”出来的，不在静态网格里）；
- 贴图可能是 **JPG**，而且引用方式五花八门：相对路径、Windows 绝对路径、`.fbm` 目录等。

**看一个 GLB 是不是“会动的蒙皮角色”，就看三样：**
- `skins` 存在吗？
- 网格里有 `JOINTS_0` / `WEIGHTS_0` 吗？
- `animations` 存在吗？（动作靠它）

很多 GLB 在 3D 查看器/游戏里没问题，是因为它们对这些结构“宽容”；Cesium 是 WebGL 渲染器，规则更严，于是同一批文件在 Cesium 里集体出问题。

---

## 2. 你需要先分清的一个关键概念：姿势从哪来

这是最容易误会的一点，直接决定了后面很多判断：

- **静态网格的顶点** = 模型“建模/绑定”时的那一版姿态（通常就是**站立**）。
- **动画（animations）** = 骨骼在时间轴上的运动，真正的“蹲、走、挥手”是**演**出来的。

**重要推论：** 一个文件看起来是“蹲姿”，它的静态网格很可能仍然是站姿——蹲是动画演出来的。**只要把动画删掉 / 不采样动画、把网格钉回绑定站姿，蹲姿就没了，模型会“变回”站姿。**

> 真实案例：`蹲姿1.glb` 的网格和 `person-stand1.glb` 几乎同一份站姿几何，唯一的差别是 `蹲姿1` 带了一段 3.40–3.83s 的“下蹲”动画。谁要是把它烘焙成绑定站姿，修完就“变站立了”，和另外两个模型看起来一样——这**不是**三个模型被合并，是动画被抹掉了。

## 3. 逐条问题详解

### 3.1 外部贴图没内嵌（最常见）

**现象**：模型加载成功，但表面黑色/缺失；Cesium 报 `Failed to load texture`。

**根因**：GLB 里图片用的是外部 `uri`，例如：

```
E:\old-project\character.fbm\Body_D.png
..\..\Textures\cloth.jpg
```

Cesium 通过 `data:` 或网络加载模型时，**没有能力回头去读你本机的绝对路径**。路径在谁那台机器上有效都不重要，只要不在 GLB 里就加载不到。

**判断**：查看 `images[]`，只要有 `uri` 且不以 `data:` 开头，就是外部引用（即“没内嵌”）。

**处置**：
- 把贴图文件（或它的 `.fbm` 目录）放到 **GLB 同级目录**，让工具按文件名递归找回并内嵌；
- 找不到时，工具会明确报出**缺失的文件名**和恢复指引，而不是静默失败。

### 3.2 JPG / 非 PNG 贴图

**现象**：部分带 JPG 贴图的模型在 Cesium 里材质不显示。

**根因**：glTF 规范其实允许 JPEG，但本项目积累的经验是 JPG 在 Cesium 加载链路上问题最多；早期因此统一转成 PNG。

**处置（现行：统一转 PNG）**：glTF 规范其实允许 JPEG，本项目曾一度实现「JPEG 原样保留」来规避转码膨胀（转 PNG 是**无损**编码，而照片类 JPEG 是**有损**压缩，两者对照片的效率差着数倍：实测 1024² 照片 JPEG 约 535KB → PNG 2.56MB；2048² 约 2.1MB → 10.25MB，**稳定膨胀约 5 倍**）。该方案后来被撤销（PR #3 revert），当前一律转 PNG。

所以现在的行为是：

- **所有 JPEG 都转 PNG**：用 `jpeg-js` 解码、`pngjs` 重编码，输出 `mimeType: 'image/png'`。内嵌图与外链图走同一条路径。
- **PNG 贴图原样不动**（不会二次编码）。
- **无法解码的 JPEG 按单文件报错**（`JPEG 转 PNG 失败：…`），而不是把坏字节写进输出——四分量 CMYK/YCCK、只有文件头没扫描数据等都属于这一类。批处理下该文件失败但不阻断其它文件（BR-004）。
- **转码全程在进程内用纯 JS 完成**，不依赖系统 ffmpeg——原因见 §5，这是打包版能跑的关键。
- 界面上已无「保留 JPEG 贴图原格式」复选框，`repairGlbFile` 也不再接受 `keepJpeg`；传入旧参数不会改变行为。

> **已知代价**：照片类贴图的模型修完会明显变大（如上，约 5 倍）。这是"统一转 PNG"换取 Cesium 侧稳定性的代价，真正的解法是贴图降采样而不是保留 JPEG（见 `docs/002-requirements.md` 的 M3）。若模型本身的贴图就是超大 PNG（例如 FBX 导出的 4096² 照片存成 PNG），修完依然很大——那不是转码造成的。

### 3.3 材质扩展（`KHR_materials_specular` 等）

**现象**：贴图、材质效果异常，或个别平台完全失败。

**根因**：这类扩展对 Cesium 属于“兼容风险高”的扩展，不一定会挂，但没必要冒这个险。

**处置**：从 `extensionsUsed` / `extensionsRequired` 和各材质 `extensions` 里移除 `KHR_materials_specular`。

### 3.4 蒙皮角色“加载成功但不显示”

**现象**：Cesium 日志显示加载成功、模型对象也建了，但窗口里没有人物；只看到包围体/空白。

**根因**：FBX 转出的**蒙皮** GLB（`skins` + `JOINTS_0`/`WEIGHTS_0`），Cesium 能创建对象，但蒙皮网格不一定画得出来。静态 OBJ 转的 GLB 没有这套结构，所以更容易显示。

**判断**：日志里出现 `skinned=true`（工具会打印）就是蒙皮网格。

**处置**：把蒙皮网格**烘焙成静态网格**：
- 按每个顶点 ≤4 个关节影响，用 `inverseBindMatrices` + 关节矩阵算出最终位置/法线；
- 重写 POSITION/NORMAL，**重算 accessor 的 min/max**（Cesium 用它们做剔除和取景，范围不对会“看不见”）；
- 删除 `JOINTS_0`/`WEIGHTS_0`，若烘焙了就一并删除 `skins` 和 `animations`。

### 3.5 修完“变成站姿 / 三个模型都一样”（本批新坑）

**现象**：把蹲姿、走动、站立三个角色拿去修，结果产物看起来**都是站立**，像同一个模型。

**根因**：见 §2。动作在动画里，而 3.4 的“烘焙”默认把网格钉在 **bind（绑定）站姿**上，再删掉动画 → 所有靠动画“演”姿态的角色全部回到站姿。move / stand 这类**本身就同源、又没带动画**的文件，修完更是必然相同。

**正确姿势**：对带动画的蒙皮模型，烘焙前先**采样动画、把骨骼冻结到目标帧的姿势**，再烘焙。项目里已实现：
- 支持取动画的**起始帧 / 结束帧**或**指定秒数**（内部参数 `poseTime`，`'start' | 'end' | 秒数`；多个动画选第几个用 `animationIndex`，当前默认第 0 个）；
- 支持 LINEAR（旋转用 slerp、平移/缩放用 lerp）与 STEP 两种插值；
- 无动画的文件不受影响（仍烘焙绑定站姿）。

**真实数据参考**：`蹲姿1` 冻结到动画帧后，烘焙产物的身高从站姿约 **1.85 → 1.36**，即蹲姿被保留（topY 1.18 → 0.67）。move1/stand1 因无动画、几何同源，产物仍然彼此一致——这是**符合预期的**。

### 3.6 模型其实在，但取景不对

**现象**：看着像“没加载”，其实是相机没对准/近裁剪把人物裁了。

**根因**：默认相机参数不一定覆盖小尺度人物模型。

**处置**：预览时用 **保守的近裁剪面**（`near=0.01` 级别），并优先按 **Cesium 包围球**、退而求其次按 **accessor 的 min/max** 计算取景距离。

### 3.7 重打包 GLB 的二进制坑（改代码时必看）

工具每次修复都要重新拼 GLB。这里有几个只要改坏一个就“黑屏/看不见”的细节：

- GLB 布局：12 字节头 + JSON 块（按 4 字节补齐，**用空格 0x20 补齐**）+ BIN 块（4 字节补齐）；
- 图片/顶点数据改大小后，所有 `bufferView.byteOffset/byteLength`、`buffers[0].byteLength` 必须重写；
- 新内容一律 **4 字节对齐**；
- 只支持**非交错**（无 `byteStride`）的 bufferView；
- 凡重写了 POSITION，必须**重算对应 accessor 的 min/max**。

## 4. 排查方法（给同事的操作步骤）

1. **先在普通 3D 查看器里确认模型本身是好的**——如果查看器也坏，那是模型源文件的问题，不归 Cesium。
2. **让工具输出一份“体检”日志**。工具在加载/验证时会打印：网格数、材质数、图片数、骨骼数、动画数、`skinned=`、用了哪些扩展、是否存在外部贴图、动画是否启动、Cesium 渲染错误。
3. 对着日志按优先级检查：
   - `skinned=true` → 走 §3.4/§3.5 的蒙皮流程；
   - `GLB 存在外部贴图：…` → 走 §3.1；
   - `extensionsRequired=[...]` → 对照 §3.3；
   - `Cesium 渲染错误：…` → 把错误原文和模型一起反馈；
   - 只有“加载成功但无包围球/范围”告警 → 大概率 §3.6 取景。
4. **用工具自带的 Cesium 验证窗**加载修复产物，确认能看到、姿态对，再交付。

## 5. 打包版工具的教训：运行时不要依赖系统外部程序

给工具做过 Windows 打包的同事会踩到这个坑，值得全组知道：

- 早期版本转码 JPG 用 `ffmpeg`（`spawnSync('ffmpeg', …)`）。开发机上装了 ffmpeg 一切正常；
- 但 **electron-builder 不会把 ffmpeg 打进去**，Windows 用户机器上通常也没有 → 一执行就 `spawnSync ffmpeg ENOENT`，所有带 JPG 贴图的修复全部失败；
- **原则**：桌面应用打包后，运行时只能依赖自己带进去的东西（JS 库 / `dependencies`）。外部可执行文件要么作为资源随包分发并找到它的绝对路径，要么干脆别用系统命令。

现改为 `jpeg-js` + `pngjs` 纯 JS 转码，随包即带、无需安装任何东西。（JS 库必须放 `dependencies`，放 `devDependencies` 就不会被打包。）

## 6. 修复工具使用建议

1. 单文件或整目录批量修复，输出目录自选，目录模式下会保留原目录层级。
2. 批量时单个文件失败**不中断**后续任务；失败原因会逐条列在结果里。
3. 贴图找不到时，把贴图或它的 `.fbm` 目录放到 **GLB 同级目录**再试。
4. 勾选“**带动画的蒙皮模型：烘焙为动画起始姿势**”：
   - 想要角色“停在动画里某个姿势”（例如蹲姿1 修复后保持蹲着）→ **勾选**（默认勾选）；
   - 无所谓姿态、只要模型能显示成绑定站姿即可 → 取消勾选；
   - 无动画的模型勾不勾都一样。
5. 修复后建议用工具自带验证窗加载产物，看是否显示、姿态是否符合预期。

## 7. 工具已知限制（如实告知）

- 冻结姿势目前默认取**第一个动画的起始帧**；多动画、或想取“动画中段某一帧”的场景还没有界面，需要的话可以扩展（代码已支持按秒数/首尾帧）。
- 蒙皮烘焙只处理 ≤4 关节/顶点的标准结构；只支持非交错 bufferView。
- 贴图只支持 **PNG / JPEG**：一律输出 PNG（JPEG 在进程内解码后重编码），不再有「保留 JPEG」选项；其它格式会报错并提示先转成 PNG/JPEG。
- JPEG 转码失败（含四分量 CMYK/YCCK、只有文件头没有扫描数据等）会明确报错，不影响同批其它文件。
- 工具**不做贴图降采样**。如果模型本身就带着超大 PNG 贴图，修完仍然很大。
- 预览只代表 Cesium 单机表现；最终以目标运行环境为准。

## 8. 术语速查

| 词 | 含义 |
|---|---|
| GLB | glTF 2.0 的二进制单文件容器（JSON + BIN） |
| skins / JOINTS_0 / WEIGHTS_0 | 蒙皮结构：顶点绑定到哪些骨骼关节、各占多少权重 |
| animations | 骨骼动画剪辑（“演”出来的动作） |
| bind pose | 建模/绑定时骨骼的默认姿势（通常站立） |
| bufferView / accessor | GLB 里指向二进制数据的索引结构；改了字节必须同步改它们 |
| accessor min/max | 顶点包围范围，Cesium 用其做剔除与取景 |
| KHR_materials_specular | 一种 Cesium 兼容风险较高的材质扩展 |
| .fbm | 3ds Max/FBX 导出的贴图附属目录 |
| ENOENT | 系统找不到某个文件/命令（打包版常因外部程序没随包而触发） |
